# 10 · 静态校验

```bash
npm run check        # node tools/check.mjs
```

零依赖，纯 Node，跑完即退出，不启动任何服务。约 1 秒。

## 为什么不写测试

项目约定是「不需要做测试，只用作代码静态验证」。但**一个永远通过的检查器毫无价值**，
所以下面每一项都用反向用例验证过 —— 故意注入错误，确认它真的会报错退出 1。

## 九项检查

### 1. 语法

对每个 `.js` / `.mjs` 跑 `node --check`。

依赖 `package.json` 的 `"type": "module"`，否则 Node 会把 `.js` 当 CommonJS
解析，`import` 直接报语法错。

### 2. import 路径

每条相对 `import` / `export ... from` 的目标文件必须存在。

### 3. 具名导入与导出对得上

检查 `import { a, b } from './x.js'` 里的 `a`、`b` 确实在 `x.js` 中被导出。

> 为什么需要这条：删掉一个导出后，第 1 项（语法）照样通过、
> 第 2 项（路径存在）也照样通过，只有真正执行才会报 `does not provide an export named`。
> 这项检查在重构时反复救场。

导出名的提取方式：

```js
export\s+(?:async\s+)?(?:const|let|var|function|class)\s+([A-Za-z0-9_$]+)
export\s*\{([^}]*)\}     // 再按逗号切分，取 as 之前的名字
```

### 3b. 命名空间成员调用

检查 `import * as player from './player.js'` 之后写的 `player.foo()`，
`foo` 确实被那个模块导出。

**这条是被真实 bug 逼出来的。** 移除每日任务功能时，
`farm.js` 里有两处 `player.countWater()` 没跟着删干净，
`node --check` 通过、路径检查通过、具名导入检查也通过 ——
因为 `countWater` 是通过命名空间访问的，上面三项都扫不到。
结果是游戏启动即崩（`initState`）或浇水即崩（`water`）。

现在这类错误在提交前就会被拦下：

```
✗ src/store/farm.js: player.countWater() 调用的成员没有从 ./player.js 导出
```

只匹配 `ns.member(` 的调用形式，不匹配 `ns.member` 属性访问
（后者可能是普通对象字段，误报率高）。当前项目有 50 处这类调用。

### 4. index.html 的本地引用

`<script src="./...">` 和 `<link href="./...">` 指向的文件必须存在。

### 5. DOM id 引用

`byId('x')` 用到的每个 id 都必须在 `index.html` 里存在。

```js
for (const m of code.matchAll(/\bbyId\(\s*'([^']+)'\s*\)/g)) { /* ... */ }
```

新增元素时忘了加进 HTML，这项会直接报出来。

### 6. CSS 变量

`var(--x)` 用到的每个变量都必须在某处定义过。

提取定义：`/^\s*(--[a-z0-9-]+)\s*:/gim`（扫描全部 CSS 文件）。

> 这项抓到过一次真实的遗漏：商店的吸附定位用了 `var(--hud-h)`，
> 而它只在运行时由 JS 写入，CSS 里没有声明。修法是在 `base.css`
> 加一个兜底值 `--hud-h: 64px`。

### 7. data-action 处理器覆盖

**每一项里最重要的一条。**

扫描所有 `data-action="xxx"` 的使用处，检查是否存在对应处理器。
处理器来源：

1. `actions: { ... }` 或 `*_ACTIONS = { ... }` 对象字面量里的键；
2. 弹窗回调里 `action === 'xxx'` / `action !== 'xxx'` 的显式分支。

为此 `modal.js` 的回调被写成显式分支而不是三元表达式：

```js
// 可扫描的形式
if (action === 'plant') ok = await farm.plant(plotId, cropId);
else if (action === 'buy-plant') ok = await farm.buyAndPlant(plotId, cropId);

// 不可扫描的形式（'buy-plant' 没出现在比较里）
const ok = action === 'plant'
  ? await farm.plant(plotId, cropId)
  : await farm.buyAndPlant(plotId, cropId);
```

**为什么需要这条**：这个项目重构前的旧版本里，播种弹窗生成的
`data-plant` / `data-buyplant` 按钮**没有绑定任何事件**，
整个播种流程从头到尾点不动，只能看着空地发愁。这项检查就是为它加的。

### 8. 数据表交叉一致性

直接 `import` 真正的数据模块来校验，不是文本匹配：

- 每种作物的 `stages` 都在 `STAGES` 里定义过；
- 每种作物的阶段序列都以 `ripe` 结尾；
- 作物数 ≥ 140；
- `UPGRADEABLE_SOIL_IDS` 里的 id 都在 `SOILS` 里；
- `PLOT_UNLOCK_LV.length === TOTAL_PLOTS`；
- 最后一块地的解锁等级对齐 `MAX_LEVEL`；
- 最后一级称号对齐 `MAX_LEVEL`；
- 经验曲线严格递增。

> 这项抓到过一次真实的遗漏：`legume` 形态一开始没配阶段路径，
> 生成器会 `Cannot read properties of undefined` 直接崩。
> 现在生成器里也加了同样的断言。

## 反向用例

每项检查都用注入错误的方式验证过。比如第 7 项：

```js
// 临时塞一个没有处理器的 data-action
export const tmp = `<button data-action="ghost-action">x</button>`;
```

```
$ node tools/check.mjs
发现 1 个问题：
  ✗ src/ui/views/__tmp.js: data-action="ghost-action" 找不到对应的处理器
$ echo $?
1
```

## 加一项新检查

放在 `tools/check.mjs` 的对应分节里，遵循同样的约定：

```js
const fail = (file, msg) => problems.push(`${rel(file)}: ${msg}`);
const notes = [];
```

- 用 `fail(file, msg)` 报错，`notes.push(...)` 记通过项；
- **不要 `process.exit(1)`**，让所有问题一次报全；
- 加完之后**必须写一个反向用例验证它能真的报错**，否则它可能只是个永远返回 true 的摆设。
