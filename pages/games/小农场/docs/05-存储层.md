# 05 · 存储层

## 两层结构

```
core/db.js         IndexedDB 连接、表结构声明、整表读取、事务写入
core/storage.js    存档网关：把「表 + 行」翻译成「农场对象」
```

上层（store / ui）只认 `state.farm / state.friends / state.bag / state.news`，
不需要知道它们分别落在哪张表、怎么关联。

## 一张表一件事

库名 `sun_farm_v2`（结构版本 1）。**没有任何「只有一条记录」的表**：

```js
export const SCHEMA = {
  farm:      { keyPath: 'id' },                 // 每座农场一行（玩家也是一行）
  plot:      { keyPath: ['farmId', 'id'] },     // 地块：按农场归属
  log:       { keyPath: ['farmId', 'seq'] },    // 日志：seq 0 是最新一条
  news:      { keyPath: 'seq' },                // 全镇时报
  relation:  { keyPath: ['a', 'b'] },           // 好感度：两点之间一条（a < b）
  inventory: { keyPath: 'itemId' },             // 玩家背包
  daily:     { keyPath: 'date' },               // 每日排行榜：一期一行，date 是账期开始日（14:00 切日，最多留 8 行）
};
```

关系：

```
farm 1 ── N plot        plot.farmId
farm 1 ── N log         log.farmId
news                    farmId 只标明来源，可以是空串
relation                a、b 都指向 farm.id，无序（写入前按字典序归一）
daily                   不关联农场：一天一行，stats 里按参与者（player / npc id）分账
```

`relation` 是唯一一张**「谁跟谁」**的表：好感度不属于任何一座农场，
所以既不能挂进 `farm` 行（那会变成两份、还要互相同步），
也不能塞进一个 JSON 字段（那样就没法按人查了）。复合主键 `[a, b]`
天然保证「一对只有一条」—— 前提是**写之前把两个 id 排好序**，
否则 `player|npc01` 与 `npc01|player` 会变成两条各记一半的记录。

### 为什么这么拆

旧版是 `player` / `plots` / `friends` / `pets` 四张表，有两个毛病：

1. **`player` 只有一行**，却塞着玩家农场的一切 —— 等级、金币、40 块地之外
   还有 `log`（60 条）与 `news`（80 条）两个数组。每次改一个金币，
   这两个数组都要跟着整行重写；它们跟「玩家」这件事本身也没有关系。
2. **邻居是一个内嵌了 `plots` 与 `log` 的巨型对象**，与玩家的地块
   （独立一张表）完全不对称。想按农场查日志？没有这条路。

现在：

- **玩家也是一座农场**：`farm` 表里 `kind: 'player'` 的那一行，
  与所有邻居同一形状、同一张表；
- **地块与日志各自成表**，用 `farmId` 关联回农场 —— 农场规模怎么长，
  都不会把任何一条记录撑成巨无霸；
- **日志天然可查**：`log` 表按 `[farmId, seq]` 排序，一座农场的日志就是一段主键区间。

### `farm` 行里有什么

```js
{
  id: 'player' | 'npc01',   // 主键
  kind: 'player' | 'npc',
  name, avatar,
  level, exp, coins,
  createdAt,

  // 玩家农场独有
  dog: { owned: { 品种id: true }, breed, satiety, at },   // 狗窝 / 上岗 / 粮槽
  dogHouse: { level, digDay },   // 狗窝等级（0~5，容量 +30/级）/ 上次挖宝的日期键
  progress: {                                             // 农场主成长档案
    lastSign, signStreak, signTotal,
    cropStats: { 作物id: { planted, harvested } },
    collected: { 作物id: true },                          // 图鉴收集（进过仓库，只增不减）
    specimens: { 作物id: true },                          // 图鉴点亮（做过标本）
    codexSeeds,                                           // 图鉴点亮奖种子的补偿标记（一次性）
    titles: { claimed: {}, equipped: '' },
    guide: {},
  },

  // 邻居独有
  personality, profession, schedule, steal,
  dog: { breed, satiety, at },     // 邻居的狗没有 owned，也不会有多只
  lastVisitAt, nextVisitAt,
}
```

`plots` / `log` **不在**这一行里 —— 它们在内存中挂在这座农场上，
写档时被拆回 `plot` / `log` 两张表。

## 内存结构与存档结构的对应

```js
state = {
  farm:      农场对象（含 plots / log / dog / progress）,
  friends:   邻居农场对象（同形状，32~52 位，随村庄等级增长）,
  bag:       { itemId: count },
  relations: { 'player|npc01': 37 },                 // 好感度，键是 a|b，0 不落键
  news:      [{ at, emoji, text, who, crop, cat }],  // 时报：涉及者 / 相关作物 / 分类
};
```

读档（`loadSave()`）做的事情就是把行还原成对象：

```js
const save = await loadSave();
// → { farms, plots: { farmId: [...] }, logs: { farmId: [...] }, news, relations, bag }
```

`initState()` 再用 `farmId` 把地块与日志挂回每座农场，
缺的地块补齐、名单里新增的邻居补建、名单里已经没有的孤儿农场连
地块与日志一起删掉（`dropFarms()`），最后**把补齐后的结果原样写回一次**。

一次性回写让「新加的字段」「新加的邻居」都能立刻落盘，
省掉一堆「某处补丁要顺手存一下」的散落逻辑 —— 32 座农场、200 多行，
一次事务也就几毫秒。

## 事务

### 提交的单位是「农场」

```js
import { commit } from '../core/storage.js';

await commit({
  farms: [state.farm],        // 写行 + 全部地块 + 整段日志
  bag: state.bag,             // 背包全量覆盖
  news: state.news,           // 时报全量覆盖（可选）
  relations: state.relations, // 好感度全量覆盖（可选）
});
```

`farms` 里的每座农场会被写三份：

1. 行本身（去掉 `plots` / `log`）；
2. 它的全部地块（`{ ...plot, farmId }`）；
3. 它的整段日志（先按 `[farmId, 0] ~ [farmId, 1e9]` 删掉，再按 `seq` 重写）。

**为什么整体重写而不是增量**：地块 ≤ 40 行、日志 ≤ 60 行，一次几百次 put
在 IndexedDB 里是一两毫秒的事；而增量要维护「哪些是新条目、哪些被挤掉了」，
错了就是脏数据。整体重写不可能对不上。

邻居结算（`persistFriends`）会把玩家农场与 32 座邻居一起提交，
所以不会出现「邻居偷了但玩家地没变」的中间态。

> **重要**：`write()` 的回调必须**同步**发出所有请求。
> IndexedDB 事务在事件循环回到空转时会自动提交，中途 `await` 会让事务失效。

### 背包 / 时报 / 好感度为什么全量覆盖

三者体量都很小（背包几百条上限、时报 240 条、好感度最多 528 对），
`clear()` + 重写最不容易出错。

- `news` 只在「会写时报的操作」里带上：收获升级、被狗抓、寻宝大奖、邻居演出；
- `relations` 只在**会动关系**的操作里带上（偷菜、帮邻居照料、送礼、邻居结算）。
  不带就等于整张表重写一遍 —— 几十位邻居的每次落盘都多写几百行，纯属浪费。
  0 值不落键，实际行数远小于理论上限。
- `dailyRows` **不挂在别的提交上**：`store/daily.js` 自己防抖落盘（400ms 合并），
  跨天结算那次才连同 farm / bag / news 一起写（奖发在那些表里）。

## 清档

```js
import { wipeSave } from '../core/storage.js';
await wipeSave();     // 清空七张表，不删库
```

目前唯一的调用点是「导入存档」（见下），**没有「重新开始」入口** ——
误触一次就是真丢档，不给这个按钮。

## 存档的导出与导入

存档只活在浏览器 IndexedDB 里，没有后端。换个 origin、清一次站点数据、
换台设备、iOS 上七天没打开，农场就没了，而且找不回来。
所以给玩家一个「把存档拿在自己手里」的出口：**⚙️ 设置**页（`ui/subpages/settings.js`）。

### 导出

`core/backup.js` 的 `exportSave()` 把 `loadSave()` 的整份结果打成一个 zip：

| 条目 | 内容 |
| --- | --- |
| `manifest.json` | `format` / `version` / `dbName` / `dbVersion` / `exportedAt` / `checksum` / `size` / `summary` |
| `save.json` | 七张表的原始行，就是 `loadSave()` 的返回体 |
| `README.txt` | 人话说明：这是什么游戏的存档、怎么导回去、导入会覆盖 |

zip 的读写是自己写的（`core/zip.js`，零依赖）：`writeZip()` 优先用
`CompressionStream('deflate-raw')`，环境不支持就退化成 store（不压缩）；
`readZip()` 从尾部找 EOCD、再走中央目录，method 0 直切、method 8 交给
`DecompressionStream`。文件名 `ximi-farm-<时间戳>.zip`。

**导出前先 `flushDaily()`**：排行榜的记账是 400ms 防抖落库的，
不冲一次的话，刚打完的那局成绩不在 zip 里。

### 导入的五步校验

`readSaveFile(file)` 任何一步不过都直接拒绝，**不碰现有存档**：

1. 是不是 zip（`readZip` 抛错就返回「不是有效的 zip 文件」）
2. 有没有 `manifest.json` / `save.json`
3. `manifest.format` 是不是 `ximi-farm-save`、`version` 认不认得（比当前新就拒绝）
4. `save.json` 的字节数与 `crc32` 校验和跟 manifest 对得上吗
5. `checkShape()` 结构自检：有 `farms`、有 `player` 行、`plots`/`logs`/`bag`/`dailyRows` 是对象、`news`/`relations` 是数组

另外还有两道前置：空文件、超过 32MB 直接拒。

### 写回的顺序与那个「封库」开关

`applySave(save)` 是**先 `wipeSave()` 再整份写回**，中途失败会留个空档 ——
所以 UI 上必须先让玩家在确认框里看过「要覆盖成什么」，确认了才动库。

写回成功后还有一段危险窗口：库里已经是新档，内存里的 `state` 还是旧档。
这几百毫秒里只要有谁落一次盘（排行榜的防抖记账、心跳里的世界推进、
藏进后台时的 `flushDaily()`），就会拿旧数据把刚导进去的存档盖掉一部分。
所以：

- `store/daily.js` 的 `suspendPersist()` —— 停掉排队的那次写库，并让之后的记账空转；
- `core/storage.js` 的 `freezeWrites()` —— 把整个 `commit()` 封住。

两个标志都是模块级的，**重载后自然复位**，不需要清理。导入成功后整页
`location.reload()`，因为内存里的 `state` 没法热替换，局部刷新只会留下
半新半旧的农场。

## 与旧库的关系

`DB_NAME = 'sun_farm_v2'`，`DB_VERSION = 3`（第 3 版新增 `daily` 表）。

`sun_farm_v1`（上一版的 player / plots / friends / pets）与更早的
`homeland_farm_v2` **原样留在浏览器里，不迁移、不删除**。
这一轮结构变的是「玩家与邻居统一成 farm 行 + 地块日志拆表」，
硬迁移的收益不如重开一局，所以直接换新库。

新增表只需在 `SCHEMA` 里加一行，`onupgradeneeded` 会自动创建；
**纯新增表不改版本号也可** —— 升级只在结构不兼容时才 +1
（`daily` 表是第 3 版：库已存在的旧档会走一次 upgrade，自动补建这张表）。

## 读档补齐

新库不需要字段迁移，但读档仍然要兜底（可能写到一半、可能手改过）：

| 对象 | 兜底 |
| --- | --- |
| 玩家农场 | `progress` / `dog` 缺字段按默认补；品种 id 不认识就退回最低档；地块不足 40 块补齐；地块缺 `usable` 时按老规则（等级解锁数）折算 |
| 邻居农场 | 性格 / 职业 / 节奏 / 偷菜倾向以名单为准；等级、身家、游标以存档为准；`dog.breed` 不认识就按等级重掷 |
| 地块 | 所有时间戳字段逐个清成有限数（`undefined` 会被结构化克隆原样存下来，界面上就冒出「NaN小时」） |

## IndexedDB 的坑

1. **必须经由 http 访问**。`file://` 下 `indexedDB.open` 可能被限制，
   而且 ESM 也会被 CORS 拦住。
2. **另一个标签页升级数据库时会阻塞**。`db.onversionchange` 里主动 `close()` 让路，
   `onblocked` 时给出可读的错误提示。
3. **复合主键的 keyPath 必须每一段都有值**。`plot` 的 `['farmId', 'id']`
   少一个就是 `DataError: key path did not yield a value` ——
   新建邻居地块时忘了给 `id` 就踩过这个坑。
4. **事务不能跨 await**。见上面的说明。
