# 05 · 剧本文件编写规范

游戏内容全部在 `data/` 下的 JSON 里。这一篇讲清楚每个文件长什么样、怎么加内容。

## 目录与清单

```
data/
├── manifest.json     启动清单
├── init/             初始设置（5 个文件）
└── choices/          抉择事件（13 个文件）
```

### manifest.json

```json
{
  "version": 1,
  "note": "启动时按此清单加载。新增剧本文件只需在这里登记，无需改代码。",
  "init": [
    "init/meters.json",
    "init/config.json",
    "init/traits.json",
    "init/aspirations.json",
    "init/endings.json"
  ],
  "choices": [
    "choices/childhood.json",
    "choices/youth.json"
  ]
}
```

浏览器无法遍历目录，所以**新文件必须登记在这里**，否则不会被加载。
`init` 与 `choices` 内部顺序无所谓——合并时按内容类型归并，不按文件顺序。

## init/ 各文件

### init/meters.json

```json
{
  "meters": [
    { "id": "health", "label": "健康", "color": "#D96C5F", "icon": "heart" }
  ],
  "stages":    [ { "max": 11, "label": "童年" } ],
  "skills":    [ { "id": "knowledge", "label": "学识" } ],
  "relations": [ { "id": "family", "label": "亲情", "color": "#C77DB8" } ]
}
```

| 字段 | 说明 |
| --- | --- |
| `meters[].id` | 六项属性的键，**结算顺序与死因优先级按数组顺序** |
| `meters[].color` | 进度条与结局页配色 |
| `meters[].icon` | 对应 `ui/icons.js` 里的 key |
| `stages[].max` | 年龄上限，从小到大排列，`stageOf()` 取第一个满足的 |
| `skills[].id` / `relations[].id` | 技能与羁绊键名 |

### init/config.json

```json
{
  "initial": {
    "age": 6,
    "stats":  { "health": 60, "mood": 60, "money": 55, "energy": 60, "social": 55, "career": 40 },
    "skills": { "knowledge": 20, "cooking": 10, "fitness": 20, "charm": 15, "craft": 10 },
    "rel":    { "family": 60, "friends": 50, "love": 0 },
    "traitCount": 2
  },
  "flags": { "metLove": false, "married": false },
  "tuning": { "winAge": 80, "moodDecay": 2 },
  "grades": [ { "min": 430, "g": "传奇的一生", "c": "#C9A227" } ],
  "flagLabels": { "married": "已婚" }
}
```

五个顶层键可以分散在多个 init 文件里（比如单独建一个 `balance.json` 只放 `tuning`），加载器会合并。

### init/traits.json

```json
{ "traits": { "optimist": { "name": "乐天派", "desc": "心情正向变化 +20%" } } }
```

`desc` 只是展示文案，**实际效果写死在 `core/rules.js#applyTrait()`**。
如果加了新特质并希望它有数值效果，必须同时改 `applyTrait()`。

### init/aspirations.json

```json
{
  "aspirations": {
    "rich": {
      "name": "财富自由",
      "desc": "50 岁前攒下 80 点金钱",
      "award": "攒够了底气，往后不必为钱低头",
      "check": [
        { "age":  { "max": 50 } },
        { "stat": { "id": "money", "min": 80 } }
      ]
    }
  }
}
```

`check` 必须是**条件数组**（各项之间是与关系）。写成单个对象也能工作（会被包成数组），但推荐统一用数组。

### init/endings.json

```json
{
  "endings": {
    "health": {
      "low":  { "t": "病榻尽头", "d": "你一直透支身体……" },
      "high": { "t": "养生反噬", "d": "你每天吞下十八种保健品……" }
    },
    "win": { "t": "圆满人生", "d": "你活到了八十岁……" }
  }
}
```

每个 `meters[].id` 都必须有 `low` 与 `high`，否则 `install()` 会抛错。`win` 也必须有。

## choices/ 各文件

### 文件骨架

```json
{
  "title": "中年 30-49",
  "events": [ { "id": "e33", "..." : "..." } ]
}
```

`title` 只用于报错时定位来源，可以不写。

### 单条事件

```json
{
  "id": "e33",
  "name": "求婚",
  "min": 22,
  "max": 49,
  "once": true,
  "cond": { "flag": "metLove", "rel": { "id": "love", "min": 35 } },
  "text": "你准备好了戒指，要跟那个陪你多年的人求婚。",
  "left": {
    "label": "单膝跪地",
    "fx": { "mood": 5, "money": -5, "rel": { "family": 4, "love": 12 } },
    "flags": { "married": true },
    "milestone": "步入婚姻"
  },
  "right": {
    "label": "再等等",
    "fx": { "mood": -2, "rel": { "love": -5 } }
  }
}
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✅ | 全局唯一，惯例 `e` + 递增序号 |
| `name` | ✅ | 说话人，显示在卡头（2~4 字最佳） |
| `min` `max` | ✅ | 可出现年龄区间，闭区间，范围 6~120 |
| `text` | ✅ | 卡面正文 |
| `left` `right` | ✅ | 两个选项 |
| `once` | ❌ | true = 一生只触发一次。**新增事件请一律写 true**（保证同一局不重复出卡） |
| `cond` | ❌ | 出现条件，见下 |
| `chance` | ❌ | 出现概率 0~1，缺省 1 |

> ⚠️ **不要写任何图片字段。** 卡面不使用外部图片，加了也不会被渲染。自检脚本会检查事件里是否残留 `http://` 链接。

### 选项对象

```json
{
  "label": "单膝跪地",
  "fx": {
    "mood": 5, "money": -5,
    "rel":    { "family": 4, "love": 12 },
    "skills": { "craft": 8 }
  },
  "skills": { "craft": 8 },
  "rel":    { "family": 4 },
  "flags":  { "married": true },
  "milestone": "步入婚姻"
}
```

- `fx` 里放六项属性（`health/mood/money/energy/social/career`）+ `rel` + `skills`
- 顶层的 `skills` / `rel` 优先级高于 `fx` 里的同名键（兼容两种写法，建议统一写在 `fx` 内）
- `fx.love` 是 `fx.rel.love` 的简写，两者会相加

## 条件 DSL（cond）

`cond` 可以是**单个对象**（对象内多键 = 与），也可以是**对象数组**（各项 = 与）：

```json
"cond": { "flag": "married", "rel": { "id": "love", "min": 35 } }
"cond": [ { "flag": "married" }, { "flag": "hasChild" } ]
```

同一个对象里 `flag` 只能出现一次——需要两个 flag 就用数组。

### 支持的键

| 键 | 写法 | 门槛默认值 |
| --- | --- | --- |
| `trait` | `"trait": "foodie"` | — |
| `flag` | `"flag": "married"` | — |
| `noFlag` | `"noFlag": "hasChild"` | — |
| `skill` | `"skill": { "id": "fitness", "min": 50 }` | 50 |
| `stat` | `"stat": { "id": "money", "min": 45 }` | 40 |
| `rel` | `"rel": { "id": "love", "min": 35 }` | 30 |
| `age` | `"age": { "min": 18, "max": 50 }` | 无（只判写了的那一边） |

`skill` / `stat` / `rel` 除了 `min` 还支持 **`max`**，用来写「低于某个值才会触发」的事件：

```json
"cond": { "stat": { "id": "money", "max": 22 } }   // 拮据时才出现
"cond": { "stat": { "id": "health", "max": 24 } }  // 身体很差时才出现
```

未知键会被 `npm run check` 抓出来。

## 组合卡牌链（前置依赖）

一部分事件只在**玩家先做过某个选择**之后才会出现。做法就是：某个选项写入一个 flag，后续事件用 `cond.flag` 依赖它。

```jsonc
// 入口：写 flag
{
  "id": "pt_1", "name": "流浪猫", "min": 8, "max": 70,
  "cond": { "noFlag": "pet" },
  "text": "楼下有只三花猫，已经蹲了你三天。",
  "left":  { "label": "抱回家", "fx": { "money": -3, "mood": 5, "energy": -2 },
             "flags": { "pet": true, "petCat": true } },
  "right": { "label": "走开", "fx": { "mood": -3, "money": 1 } }
}

// 后续：只有养了狗才会抽到
{
  "id": "pt_4", "name": "遛狗", "min": 10, "max": 75,
  "cond": { "flag": "petDog" },
  "text": "它叼着绳站在门口，眼神不容拒绝。",
  "left":  { "label": "每天两小时", "fx": { "health": 4, "energy": -2, "mood": 4 },
             "skills": { "fitness": 3 } },
  "right": { "label": "楼下转转就行", "fx": { "energy": 2, "health": -1 } }
}
```

写链时的三条规矩：

1. **入口事件一定要加 `noFlag`**（如 `noFlag: pet`），否则已经养过宠物还会反复抽到「要不要养」
2. **入口加 `once: true`**，避免同一个人生大事被触发多次
3. **新 flag 必须在 `init/config.json` 的 `flags` 里登记**（并顺手在 `flagLabels` 里给它一个中文名，会显示在人生档案里）

标记也可以被置回 false 用来表达状态变化：

```jsonc
"left": { "label": "离", "flags": { "married": false, "divorced": true }, "...": "..." }
```

### 现有三条链

| 链 | 文件 | 入口 flag | 下游 flag |
| --- | --- | --- | --- |
| 宠物 | `choices/pet.json` | `pet` | `petDog` / `petCat` |
| 家庭 | `choices/family.json` | `metLove` → `married` → `hasChild` | `dating` / `childGrown` / `grandchild` / `divorced` |
| 事业 | `choices/career.json` | `biz` | `bizSuccess` / `bizFail` |

`npm run check` 的第 5 步会验证：每个被 `cond` 引用的 flag 都有选项能把它置为 true，以及三条链的入口与后续都存在。**写出一条永远走不到的死链会被报错。**

## 数值设计准则

**1. 一个选项不要同时动太多维度**
3~4 个维度最舒服。动 6 个会让玩家看不懂旁白条里的变化 chips。

**2. 正负要有取舍，别做「明显更好」的选项**

```jsonc
// ❌ 左边纯赚，没有抉择感
"left":  { "label": "去",   "fx": { "money": 5, "mood": 4, "health": 3 } },
"right": { "label": "不去", "fx": { "mood": -3 } }

// ✅ 两个方向都付出代价
"left":  { "label": "进大厂拼", "fx": { "money": 5, "career": 4, "energy": -3, "health": -3, "mood": -3 } },
"right": { "label": "进小厂",   "fx": { "career": 2, "money": 3, "energy": 3, "mood": 3 } }
```

**3. 幅度参考**

| 幅度 | 用途 | 例子 |
| --- | --- | --- |
| ±1 | 日常小事 | 买彩票、喂猫 |
| ±2 | 普通抉择 | 团建聚餐、办健身卡 |
| ±3~4 | 较重要的事 | 换工作、一次像样的旅行 |
| ±5 | 人生大事 | 手术、晋升、一次大决断 |
| ±8 | 极端单点（只有金钱用得到） | 婚宴、首付、中奖 |

除金钱外，六项属性**不要超过 ±5**；金钱上限 ±8，用来保留买房、婚宴这类大额单点。
整套剧本就是按这个幅度重映射过的（2026-10 那轮把 ±20/±12/±9 的摆幅收窄到了这里），
改数值时不要再把幅度写回去。

**4. 精力是例外，它有独立的语义分档**

精力不看「事情多重」，看「这件事是什么性质」：

| 值 | 含义 | 例子 |
| --- | --- | --- |
| 不写 `energy` | 中性事件，不耗也不恢复 | 听说消息、偶遇、旁观 |
| `-1` | 主动做一件可以做的事 | 上班、上课、办事、出门、运动 |
| `-2` | 较累的主动事 | 兼职一整天、长途通勤、带团队、搬家 |
| `-3` | **事倍功半**，只用于这类 | 通宵、拼命、连轴转、陪护、极限运动 |
| `+1` | 缓一缓 | 推掉一个安排 |
| `+2` | 小憩 | 散步、喝杯茶、早点睡 |
| `+3` | 好好休息 | 睡个整觉、周末在家 |
| `+4` | 睡饱 / 度假 / 请个长假 | 休个长假、睡到自然醒 |

两条硬规矩（写错了就是语义错配，`tools/` 下的语义扫描能抓出来）：

- **放松、休息、回避、拒绝类选项不能是负精力**——「回家睡觉」写成 `-2` 是 bug
- **通宵、陪护、搬家、极限这类硬活不能是正精力**——「通宵赶完」写成 `+4` 是 bug

> 历史教训：这套分档上线前，剧本里有 296 个选项的精力在 -5 ~ -9，
> 平均每扣 3.5 点，随机玩法 48 回合就油尽灯枯；同时又有 28 处语义颠倒
> （该恢复的在扣、硬活在恢复）。重映射后随机玩法平均 62 回合、
> 38% 寿终正寝，专挑耗精力选项的「拼命三郎」终局精力约 32——付得出代价，但不会常态崩盘。

**4. 年龄区间要留重叠**
不要在 17/18 一刀切。全年龄事件给 `"min": 6, "max": 120`，能在任何阶段兜底。

**5. 文案要有画面感，别写说明文**

```jsonc
// ❌ "text": "你面临着职业发展与身体健康之间的权衡。"
// ✅ "text": "连续加班三个月，体检亮起黄灯。"
```

## 添加内容的完整流程

**加一条事件**（文件已存在）：直接往 `choices/xxx.json` 的 `events` 数组里追加一个新 `id`。

id 命名惯例分四代，保持唯一即可：

| 世代 | 命名 | 例子 |
| --- | --- | --- |
| 最初 78 条 | `e` + 序号 | `e1` ~ `e78` |
| 阶段扩充 | 阶段前缀 + `_a` / `_b` + 序号 | `ch_a1`、`sn_b12` |
| 组合链 | 链前缀 + 序号 或 链前缀 + `_b` | `pt_4`、`fm_13`、`cr_b5`、`lf_a1` |
| 二次扩充（200 条） | 上述前缀 + `_c` + 序号 | `ch_c1`、`pr_c20`、`tr_c8`、`lf_c16` |
| 组合事件集（208 条） | 新链前缀 + 序号 | `car_1`、`fr_s2`、`jb_tech3`、`sc_d1`、`fp_10`、`mo_5`、`he_2`、`dv_9`、`bz_12`、`fa_4` |

各文件的前缀对照：

| 前缀 | 文件 | 含义 |
| --- | --- | --- |
| `fr_1~6` | `friends.json` | 结交某类朋友（入口，置 flag） |
| `fr_s*` `fr_t*` `fr_r*` `fr_k*` `fr_a*` `fr_n*` | `friends.json` | 球友 / 学伴 / 阔朋友 / 江湖朋友 / 文艺朋友 / 网友的专属事件池 |
| `sc_*` | `school.json` | 校园事件 |
| `sc_d*` | `school.json` | 辍学链（入口 `sc_d0~d2`，后续 `sc_d3~d7`） |
| `jb_1~3` | `jobs.json` | 择业（入口，置 `jobSet` + 某个 `jobXxx`） |
| `jb_tech*` `jb_med*` `jb_edu*` `jb_gov*` `jb_biz*` `jb_cf*` | `jobs.json` | 技术 / 医护 / 教师 / 体制内 / 商务 / 技工 六条职业线 |
| `jb_g*` | `jobs.json` | 通用职场事件（`degree` 即可抽） |
| `car_*` | `car.json` | 驾照 → 买车 → 用车 → 事故 → 收束 |
| `fp_*` | `family-plus.json` | 家庭补充 |
| `mo_*` | `money-line.json` | 投资理财 + 房子 |
| `he_*` | `health-line.json` | 体检 → 大病 → 康复 / 转慢性 |
| `dv_*` | `divorce.json` | 离婚之后 |
| `bz_*` | `biz-line.json` | 创业成败之后 + 自己开店 |
| `fa_*` | `fame.json` | 名声线 |

新写的事件推荐用**阶段前缀或链前缀**，一眼能看出它属于哪儿（`ch` 童年、`yt` 少年、`ad` 青年、`pr` 中年、`sn` 知命、`el` 晚年、`cm` 通用、`tr` 特质、`gt` 门槛、`pt` 宠物、`fm` 家庭、`cr` 事业、`lf` 生活支线）。

⚠️ 新事件请保留 `"once": true`。这是「同一局不重复出同一张卡」的保证，去掉它会让玩家在长局里反复刷到同一张脸。

**加一个剧本文件**：
1. 在 `data/choices/` 新建 JSON
2. 在 `data/manifest.json` 的 `choices` 数组里登记相对路径
3. 跑 `npm run check`

**改数值**：编辑 `data/init/config.json` 的 `tuning`，刷新浏览器即可。

不管改什么，最后都跑一遍：

```bash
npm run check
# [1] 剧本加载
#   ✓ 29 个 JSON 文件加载完成
#   ✓ 1026 条抉择 · 6 项属性 · 8 种特质 · 4 种心愿
# [2] 数据校验
#   ✓ 1026 条事件合法（id 唯一、选项完整、无任何外部资源引用）
# [7] 事件规模与单局去重
#   ✓ 中年（30-49）590 条可抽事件，覆盖 20 年
#   ✓ 40 局随机试玩：单局内零重复事件
```

自检会检查：JSON 可解析、manifest 格式、事件 id 唯一、左右选项完整、年龄区间合法、无外部链接、cond 键合法、结局文案齐全、**组合链没有死链**，最后跑 40 局随机试玩验证单局不重复并统计各阶段事件池深度。

## 常见坑

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 新文件没生效 | 忘了在 manifest 登记 | 加到 `init` 或 `choices` 数组 |
| 启动白屏并提示「剧本加载失败」 | JSON 语法错（多余逗号、注释） | JSON 不支持注释；用编辑器校验 |
| 事件永远不出现 | `cond` 里的 flag / id 拼错 | 对照 `init/config.json` 的 `flags` 与 `meters.json` |
| 两个 flag 条件只生效一个 | 写在了同一个 cond 对象里 | 拆成数组：`[{flag:'a'},{flag:'b'}]` |
| 属性没变化 | `fx` 键名不是六项属性之一 | 对照 `init/meters.json` 的 `meters[].id` |
| 技能/羁绊没变化 | 写成了 `"fx": { "fitness": 8 }` | 应该是 `"fx": { "skills": { "fitness": 8 } }` |
| 卡面仍是旧内容 | 浏览器缓存 | `serve.mjs` 已设 `no-cache`；硬刷新 Ctrl+F5 |
| 页面提示「剧本加载失败」且是 HTTP 404 | `file://` 打开或路径不对 | 用 `npm run dev`，确认 `data/` 与 `index.html` 同级 |
| **条件永远不成立（事件从不出现）** | `skill` / `stat` / `rel` 只写了 `max` 没写 `min`，引擎会用默认下限补齐（技能 50 / 属性 40 / 羁绊 30），变成「≥50 且 ≤35」这种自相矛盾的条件 | 想要「低于某值才触发」必须显式写 `"min": 0`：`{ "stat": { "id": "money", "min": 0, "max": 45 } }` |
| 新 flag 加进 `flags` 却没加进 `flagLabels` | 人生档案里显示成空白 | 两个对象成对维护，新增标记必须同时写中文名 |

## 组合事件集（事件线）的写法

一条「事件线」= 入口卡（置 flag） + 若干依赖该 flag 的后续卡。四条硬性规矩：

1. **入口必须带 `noFlag`**（如 `{"noFlag":"jobSet"}`），否则已经择业还会反复抽到「要不要择业」。
2. **入口 `once: true`**，并且**新 flag 必须在 `init/config.json` 的 `flags` 与 `flagLabels` 里同时登记**，否则 `npm run check` 第 5 步会报死链、人生档案里也会显示空白。
3. **不该每局都发生的节点用 `chance`**：`"chance": 0.12` 表示每次入池只有 12% 概率被抽中。车祸、爆仓、翻车、并发症这类都靠它控制。
4. **想「低于某值才触发」，`min` 必须显式写 0**（见下面的常见坑）。

### 池子深度决定触发率（重要）

`pickEvent` 在候选池里按权重抽一张。权重由 `tuning.chainWeight` 控制：

| chainWeight | 效果 |
| --- | --- |
| `1` | 全部等概率（原行为） |
| `2` | cond 里引用了 flag 的卡（＝玩家已经走上这条线）权重翻倍，即「事件线提一级」 |

默认 `2`。实测（400 局）：链卡在抽到的卡里占比由 12.6% 提到 20.0%，而 400 局触达的不同事件数由 911 升到 935——入口卡只是轻微让位，整体可见内容反而更多。

但**加权只解决「已经在线上」的卡**。一张卡能不能被看到，主要还是看池深：

| 阶段 | 池深 |
| --- | --- |
| 童年 6-11 | 115 |
| 少年 12-17 | 232 |
| 青年 18-29 | 508 |
| 中年 30-49 | 590 |
| 知命 50-64 | 524 |
| 晚年 65-79 | 364 |

推论：**越晚的人生阶段，单张卡越难被看到**。想让某条线更容易出现，把入口前移到少年／青年，或者多写几张卡提高该线在池中的占比。另外，链卡还要再乘一层上游 flag 自身的触发率——上游本来就稀有（实测 `hasChild` 约 7%、`bizSuccess` 约 0%），二级链就接近不可见。**遇到某个标记长期为 0%，先查它的上游 flag 而不是继续加卡。**
