## GitHub 404 修复（同日再追加）

用户报 404，错误体 documentation_url 指向 get-repository-content（contents GET）。

诊断：pull() 本来就会把 404 当"文件不存在"吞掉返回 null，所以 Network 面板里出现这个 404 是正常的探测请求；但如果同步真的失败，根因是手动输入的新分支在仓库里并不存在，push 也 404——上一轮的"手动输入分支"只记了名字没真建分支。

修复（`js/config-sync.js`）：
- `githubFetch` 错误对象带出 GitHub 返回的原始 message，页面日志可看到具体原因；401/403/404/409 分别给中文说明。
- `GitHubAdapter.ensureBranch()`：分支不存在时从默认分支新建；空仓库无提交时先 `seedDefaultBranch()` 写入空配置作初始提交，再建分支。
- `ConfigSync.sync()` 在 push 前调用 ensureBranch；若真的新建了分支，重新 pull 一次取 sha 再 push（避免无 sha 更新失败），丢弃这次 pull 的合并结果，只更新 sha。
- 语法检查通过。真实 GitHub 调用仍需用户 token 验证。

结论：若只是 Network 面板看到红色 404，那是正常探测；若同步失败，现应能自动建分支解决。

## 404 处理简化（同日再追加）

用户纠正：第一次提交文件时 GET 404 是正常的"文件不存在"信号，应直接新建文件，不该每次同步都跑建分支探测（ensureBranch 每次多 2~3 次 API 且逻辑复杂）。

改回简洁流程（`js/config-sync.js`）：
- `pull()` 捕获 404 → `sha = null` 并返回 null（文件不存在）。
- `push()` 拆成 `writeFile()` + 兜底：直接以无 sha 的 PUT 新建文件（contents API 创建文件不需要 sha）；只有写文件仍 404 且无 sha（说明分支真不存在）时才 `createBranch()` 后重试一次。
- `createBranch()` 替代原 `ensureBranch()`：从默认分支 ref 建分支；空仓库先 `seedDefaultBranch()` 写 `.gitkeep` 占位作初始提交（不再写配置文件本身，否则新分支上文件已存在、重试 PUT 会 409）。
- `sync()` 删掉 prepare/二次 pull，pull 后直接 push。

验证：JS 语法通过；无 ensureBranch 残留。经验：contents API 创建文件无需 sha，PUT 到不存在分支才 404，建分支走 /git/refs。

## 404 真因：repo 未拆分（同日再追加）

用户给出实际请求 URL：`/repos/Verlif/Verlif%2Ffor-test/contents/config.json` —— `%2F` 说明 repo 段含斜杠。

根因：`el.ghBind` 绑定时 owner 用了 `splitRepo()` 的短名，repo 却误用了 `el.ghRepo.value` 完整名 `Verlif/for-test`；adapter 的 `contentPath` 对每段做 encodeURIComponent，斜杠变 `%2F`，路径指向不存在的仓库 → 必然 404。listBranches 用的是拆分后的 owner/repo 所以拉分支正常，只有 contents 读写错，很有迷惑性。

修复（`js/app.js`）：
- 绑定时 `repo: target.repo` 存短名；`updateBadge` 和绑定日志改显示 `owner/repo`。
- `restoreBinding` 用 `binding.owner + '/' + binding.repo` 去 repoCache（存的是 fullName）匹配并回填输入框。
- `loadBinding` 加旧数据兼容：repo 含 `/` 时拆分修正 owner/repo 并回写 localStorage，用户无需重新绑定。

验证：JS 语法通过；本地脚本比对路径，修复后为 `/repos/Verlif/for-test/contents/config.json?ref=master`。经验：GitHub fullName 必须拆成两段，owner/repo 各自编码；不要把 fullName 直接当 repo 传入。

- 语法检查通过，无头截图确认「记住 token」复选框与链接布局正常（截图已清理）。

经验：PAT 明文存浏览器是纯前端固有限制，缓解手段是细粒度 + 短过期 + 不记住时 sessionStorage；彻底解决需后端代理 OAuth。

## 403 Resource not accessible 排查（同日再追加）

用户按细粒度 token 步骤操作后同步失败：`Resource not accessible by personal access token`。

诊断：fine-grained token 权限不足的典型错误，最常见是 Contents 停在默认 Read-only（读可过、写被拒），或 Repository access 未真正勾选目标仓库。修法：token 详情页 Edit permissions → Contents 改 Read and write → 保存，token 值不变无需重签；确认目标仓库已勾选。若仍失败检查 Resource owner / 组织批准。

改动：`js/config-sync.js` 的 403 提示改为「确认 token 的 Contents 为 Read and write、目标仓库已勾选」；`index.html` 帮助弹窗加橙色排查区说明该错误成因与修法；`css/style.css` 加 `.trouble` 样式。无头截图确认排查区完整显示。

经验：细粒度 token 权限逐项默认 No access / Read-only，Contents 写权限必须手动改；GitHub 官方提示可用 `X-Accepted-GitHub-Permissions` 响应头确认端点所需权限。改 token 权限后 token 串不变、即时生效，不用重新生成。
