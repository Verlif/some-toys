# 局域网聊天室

基于 **WebRTC DataChannel** 的点对点聊天工具。**不需要服务器、不需要账号、不上云**：  
连接双方通过手动交换一段「邀请码 / 应答码」（或直接扫二维码）完成握手，之后消息与文件都在两台设备之间直连传输。

---

## 快速开始

ES Module 必须通过 HTTP 协议加载，**不能直接双击 `index.html`**。用自带的零依赖静态服务器启动：

```bash
node tools/serve.mjs          # 默认 http://localhost:5173
node tools/serve.mjs 8080     # 指定端口
```

启动后终端会同时打印本机地址与局域网地址，两台设备各自打开同一个页面即可开始连接。

## 使用流程

### 一方创建，另一方接受

| 步骤 | 发起方（创建连接）                      | 接收方（接受连接）             |
| -- | ------------------------------ | --------------------- |
| 1  | 点「生成邀请码」，得到一串 `SIG1:...` 并自动复制 | 粘贴 / 扫码拿到邀请码，点「生成应答码」 |
| 2  | 把邀请码发给对方（文本、链接或二维码）            | 把应答码发回给对方（文本、链接或二维码）  |
| 3  | 粘贴 / 扫码拿到应答码，点「完成连接」           | ——                    |

连接建立后左侧会自动出现联系人，选中即可聊天、传文件。第一个连接会自动选中。

### 昵称会同步给所有已连接的对方

点自己的昵称改名后，会**立即广播给所有在线的连接**，对方的侧栏、聊天标题会同步更新，并在会话里留下一条「A 改名为 B」的系统提示。改名时如果没有任何在线连接，会明确提示「当前没有在线连接可同步」。

此外，每次连接建立的那一刻双方会再对一次昵称，所以「对方生成了邀请码之后才改名」这种时序差也能收敛到最新名字。

### 图片可以直接预览

发送或接收图片（`image/*`，或扩展名属于 png / jpg / jpeg / gif / webp / bmp / avif / svg / ico）时：

- 传输过程中显示常规文件卡片与进度条，**传完才换成缩略图**，所以不会有布局跳动
- 缩略图限制在 300px 高以内，保持原始比例不裁剪
- 点击缩略图打开全屏预览，右上角可下载原图；点图片、点空白或按 Esc 关闭

对端如果是不带 MIME 的旧版本，接收侧会按文件扩展名兜底判断，因此新旧版本互传图片同样能预览。

### 码输入框的容错

两个粘贴框对粘贴内容做了归一化，下面这些都是**可以直接粘贴且按钮立刻可用**的：

- 裸码：`SIG1:H4sIAAAA...`
- 分享链接：`http://192.168.x.x:5173/#code=SIG1%3AH4sIAAAA...`
- 带说明文字的码：`邀请码：SIG1:H4sIAAAA...`
- 被 IM 换行 / 加了尾注的码：`SIG1:H4sIAAAA...\n共 812 字符`

粘贴后输入框会**自动改写成裸码**。如果内容确实不是有效的码，下方会出现一条黄色提示说明原因，不会让你对着一个不亮的按钮猜。

### 依赖原生对话框的地方已全部替换

昵称修改、大文件发送确认原本用的是浏览器的 `prompt` / `confirm`，现在统一走站内对话框（`ui/dialog.js`），样式与整体一致，移动端观感也统一，并且不会阻塞页面渲染。

### 二维码与分享链接

二维码里编码的是 **「当前页面地址 + `#code=信令码`」**，所以它有两种被扫到的场景：

| 谁扫                | 结果                       |
| ----------------- | ------------------------ |
| **手机系统相机 / 微信扫码** | 直接打开本页，并自动把码填好、跳到对应流程    |
| **本页内置的「扫描二维码」**  | 只把其中的信令码提取出来填入输入框，不做任何跳转 |

- **生成时**：每生成一个邀请码或应答码，面板下方会同步渲染二维码，可点「放大显示」铺满屏幕。
- **读取时**：粘贴框旁边就是「扫描二维码」，点开调用摄像头实时识别，成功后自动填码并放开下一步按钮。
- **降级**：摄像头不可用时（无权限 / 非 HTTPS / 无摄像头），扫码遮罩里可切到「从图片识别」选一张二维码图片识别；也可以直接手动粘贴。
- 除了二维码，还有 **「复制链接」** 按钮：把链接发给对方，点开同样直达并自动填码。

> **关于应答码的链接**：邀请码链接可以直接打开（打开者就是要接受连接的一方）。  
> 但应答码只有**对应的发起方**能用 —— 而它依赖的协商上下文保存在发起方**当前这个页面的内存里**。  
> 所以如果一个全新的页面通过链接拿到应答码，是无法完成连接的，界面上会明确提示；  
> 正确做法是回到发起连接的那个页面，用「扫描二维码」读取。

> 信号码长度约 700~1200 字符，加上链接前缀后二维码矩阵通常在 110×110 模块左右，属于「比较密」的码。  
> 手机上尽量让二维码充满取景框、光线均匀、屏幕亮度调高，识别率最高。  
> 若极端情况下超过二维码容量上限，会自动回退为「纯码二维码」并在界面上说明。

### 拖拽发送文件

把文件直接拖到窗口任意位置即可发送给当前聊天对象，支持一次拖入多个文件（按顺序逐个传输）。  
拖拽期间会出现落区提示；未选择聊天对象或对方不在线时会给出提示而不发送。

## 分辨率适配

| 断点                  | 形态                                                    |
| ------------------- | ----------------------------------------------------- |
| **PC** ≥ 1024px     | 侧栏 268px 常驻，双栏布局                                      |
| **平板** 768 ~ 1023px | 侧栏收窄至 220px 常驻，内边距与气泡宽度同步压缩                           |
| **手机** < 768px      | 侧栏变为抽屉：左上角 ☰ 滑出，点选联系人后自动收起；模态框改为底部弹层（带把手）；输入区适配键盘与安全区 |

同时处理了横屏矮屏、`100dvh` 移动端地址栏、iOS 聚焦缩放（输入框 16px）、`safe-area-inset` 等细节。

**分层规则**：`utils → core → ui`，依赖单向。`core` 层通过 `utils/bus.js` 事件总线把状态变化广播给 `ui` 层，因此核心逻辑不依赖任何 DOM —— 25 个模块都能直接在 node 下 `import` 验证，便于单独复用与替换界面。

### DataChannel 消息协议

一条连接上跑的都是 JSON 文本帧，用 `type` 区分：

| type | 载荷 | 说明 |
| --- | --- | --- |
| `chat` | `{ text }` | 文本消息 |
| `name` | `{ name }` | 昵称变更 / 握手时的昵称对齐 |
| `file-start` | `{ fileId, name, size, mime, totalChunks }` | 文件头，`mime` 为后加字段 |
| `file-chunk` | `{ fileId, index, data }` | 分片，`data` 为 base64 |
| `file-end` | `{ fileId }` | 传输结束 |

后加字段都做了向后兼容：旧版本收到不认识的 `type` 直接忽略，收到缺少 `mime` 的 `file-start` 会按扩展名兜底判断。

### 消息渲染为什么是增量的

一条消息**只创建一次 DOM 节点**，之后一直复用：

- 新节点才挂 `.is-new` 播放入场动画，`animationend` 后立刻摘掉标记类
- 文件传输中的进度更新只改 `.file-meta` 文字与 `.progress-fill` 的宽度，不重建节点
- 切换会话时才整屏重建，并释放旧会话的节点引用
- 只有「贴底」或「自己发了新消息」时才自动滚到底部，翻看历史时不会被进度更新拽走

这样发送消息、上传进度、点击下载都不会引起整屏闪烁，也不会打断正在进行的下载。

## 静态校验

```bash
node tools/check.mjs
```

七项检查，全部零依赖、无需浏览器：

1. 逐文件 `node --check` 校验 ES Module 语法
2. 校验 `index.html` 中引用的 CSS / JS / vendor 资源是否存在
3. 校验所有 `import` 相对路径能否解析到真实文件
4. 交叉校验 JS 里用到的 DOM id 是否都在 `index.html` 中存在
5. 检查 CSS 括号配平
6. 检查 CSS 变量的引用是否都有定义
7. 检查 `<use href="#i-xxx">` 图标引用是否都能在雪碧图里找到

## 已知限制

- **摄像头扫码需要安全上下文**。浏览器只在 `localhost` 或 HTTPS 下允许 `getUserMedia`。用局域网 IP 以 http 打开时会自动提示并降级为「从图片识别」或手动粘贴。  
  临时方案：Chrome 打开 `chrome://flags/#unsafely-treat-insecure-origin-as-secure`，把局域网地址加进白名单并重启浏览器。
- 应答码链接无法在全新页面完成连接（见上文「关于应答码的链接」），这是手动信令协议的固有限制。
- 手动信令为**非 trickle 模式**，需等 ICE 收集完成（默认最多 4 秒）才出码，双方交换一次即可，之后不支持中途改网络环境。
- 位于对称 NAT / 严格企业防火墙后的两台设备可能无法直连（仅配置了公共 STUN，没有 TURN 中继）。
- 文件传输基于 DataChannel 单通道，未做断点续传；单文件超过 500MB 会二次确认。
- 信令码格式 `SIG0:` / `SIG1:` 与旧版单文件实现**完全一致**，新旧版本之间可以互相连接。

## 兼容性

依赖 `RTCPeerConnection`、`RTCDataChannel`、`CompressionStream`（无则自动降级为 `SIG0`）、`URLSearchParams`、CSS `dvh` / `clamp()` / `aspect-ratio`。  
推荐 Chrome / Edge / Safari 的最新版本。iOS Safari 需 14.3+ 才支持 `CompressionStream`，更低版本会走 `SIG0` 降级（码更长，二维码会更密）。
