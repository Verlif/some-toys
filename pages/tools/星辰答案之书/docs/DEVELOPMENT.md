# 开发文档

面向要改动这个项目的人。README 讲"怎么用"，本文讲"为什么这么写"。

---

## 1. 技术选型与约束

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 模块化 | **经典 `<script>` + 全局命名空间**，非 ES Modules | ES Modules 在 `file://` 下会被 CORS 拦截。这个项目是"双击就能看"的玩具页，保持零门槛优先于模块语法糖 |
| 构建 | **无构建** | 页面本身就是产物，改完刷新即见 |
| 依赖 | **零依赖** | 全部手写，Canvas 2D 足够 |
| 命名空间 | `window.AnswerBook` | 各文件 IIFE 内挂载，避免污染全局 |
| 语法 | ES5 为主 + `Promise` | 老设备兼容性留有余量，不引入转译需求 |

> 若将来需要打包，把 `index.html` 里的 `<script>` 换成打包器入口即可，
> 各模块的 IIFE 结构可以原样保留。

### 加载顺序是硬约束

`index.html` 中脚本按依赖拓扑排序，**不可调换**：

```
utils/math  utils/random  config
    └─ core/viewport  core/loop
    └─ data/texts.fallback  data/texts
    └─ scene/sprites  scene/stars  scene/meteors  scene/blackhole
    └─ ui/answer-text
    └─ main
```

原因是多数模块在 IIFE 执行期就会读取 `NS.config.*` 与 `NS.viewport`，
而不是等到运行时才取。加新模块时请插到它依赖项之后。

## 2. 分层结构

```
main.js          装配 + 主循环
  ├─ core/*      与画面无关的运行时（尺寸、帧循环）
  ├─ data/*      数据加载
  ├─ scene/*     画面元素（各自管自己的状态、更新、绘制）
  └─ ui/*        与用户直接交互的展示层
```

各层之间**只通过 `AnswerBook` 命名空间通信**，不互相 `require`。
`config.js` 是唯一的参数来源，不建议在业务代码里写裸数字。

### 模块职责一览

| 文件 | 职责 | 对外接口 |
| --- | --- | --- |
| `core/viewport.js` | 测量视口、按 DPR 建立后备缓冲、广播 resize | `init` `resize` `onResize` `width/height/ctx` |
| `core/loop.js` | 把 rAF 折算成秒级 dt | `start(step)` `maxDt` |
| `data/texts.js` | 加载并解析文案 | `loadTexts(url)` `parseTexts(raw)` |
| `scene/sprites.js` | 预渲染星点光晕贴图 | `white` `blue` `gold` `pool` |
| `scene/trail.js` | 通用尾流：按时间采样位置点 | `create(spanSec, steps)` |
| `scene/stars.js` | 星场状态与绘制 | `list` `build` `respawn` `update` `drawTrails` `draw` |
| `scene/meteors.js` | 流星生成与绘制 | `list` `spawn` `update` `draw` |
| `scene/blackhole.js` | 黑洞运动、引力与吸积流耦合、渲染 | `list` `spawn` `update` `attract` `draw` |
| `ui/answer-text.js` | 文案轮播调度 | `start()` |

## 3. 渲染管线

### 3.1 图层与 z-index

| 层 | 载体 | z-index |
| --- | --- | --- |
| 星云 | `#nebula`（CSS 径向渐变 + blur） | 0 |
| 星辰 / 流星 / 黑洞 | `#sky`（单个 Canvas） | 1 |
| 暗角 | `#vignette`（CSS 径向渐变） | 2 |
| 答案文本 | `#stage > #text` | 3 |

只有一个 Canvas。星云和暗角用 CSS 做，省掉每帧的模糊运算。

### 3.2 坐标系

`viewport.resize()` 里一次性执行 `ctx.setTransform(dpr, 0, 0, dpr, 0, 0)`，
把设备像素比烘进变换矩阵。**之后所有绘制代码一律使用 CSS 像素坐标**，
不需要再乘 DPR。`clearRect(0, 0, width, height)` 同理。

DPR 上限为 2（`viewport.maxDpr`），4K 屏上不至于让像素量翻四倍。

### 3.3 每帧顺序

`main.js` 的 `frame()`：

```
clearRect
blackhole.update(dt)           // 黑球移动 / 回收
blackhole.attract(stars, dt)   // 引力 + 吸积流耦合，改写速度；落入球内则吞没
stars.update(dt)               // 速度积分出位移，并把位置喂给各自的尾流
stars.drawTrails()             // 尾流
stars.draw(now)                // 星点本体，压在尾流之上
meteors.update(dt); meteors.draw()
blackhole.draw()               // 黑球最后画，盖住一切
```

三条顺序约束，改动时注意：

1. `attract` 必须排在 `stars.update` 之前 —— 先施力再积分，速度的改变才当帧变成位移；
2. 尾流要画在星点**之前** —— 否则那条亮线会从星点头上压过去，像被穿过；
3. 黑球要画在**最后** —— 它核心是不透明的纯黑，既盖住被吞没的星，也盖住所有尾流的
   内侧端点，星点才会看起来是"沉进去"而不是"贴在球面上"。

### 3.4 dt 钳制

`loop.maxDt = 0.05`。切走标签页再切回来时 rAF 的间隔可能是几秒，
不钳制的话星场会瞬间被"弹射"出去。

### 3.5 流星：把速度压慢、把角度说清楚

流星复用的就是 `scene/trail.js`，所以"尾巴有多长"和星辰是同一套机制
（长度 = 速度 × `trailSpan`）。它自己只需要解决两件事：

**① 速度必须压慢。** 真实流星在屏幕上只存在零点几秒，看到的是一道一闪而过的
划痕，既看不出方向也看不出角度。当前取 240~500 px/s，横穿画面要好几秒，
角度才读得出来；配合 `trailSpan = 0.5` 得到约 120~250px 的尾巴。

**② 角度与入射边绑定：**

| 与水平夹角 | 起点 |
| --- | --- |
| > 45°（陡坠） | 屏幕上方 |
| ≤ 45°（平掠） | 屏幕左侧或右侧 |

一律从上方生成的话，浅角度的流星得先在屏幕外横着飞很久才露头 ——
看起来像"迟到"，该出现的时候没出现。

**③ 寿命由几何算出，不是猜的**（`spawn` 内）：

```js
tx = 到左右边界的距离 / |vx|
ty = 到下边界的距离 / vy
lifeMax = min(tx, ty)
```

于是无论角度多缓、速度多快，流星总是刚好飞完一程：既不会在半空中凭空消失，
也不会在画面外空跑掉一半寿命。亮度包络仍按 `age / lifeMax` 取比例
（前 10% 点亮、后 28% 熄灭）。

## 4. 黑洞：实现说明

这是全项目最复杂的一块，改动前请先读完本节。

造型上它只是**一个纯黑圆**。而它对星点做的事**完全交给牛顿力学** ——
没有任何"入轨""绕圈"之类的状态机或参数化轨道。星点永远只是一个被积分的质点：

```
a = 引力(径向) + 吸积流耦合(耗散拖曳)
v += a · dt                       ← 惯性在这里
x += v · dt
```

### 4.1 两项力，各司其职

| 力 | 形式 | 作用 |
| --- | --- | --- |
| 引力 | `a = gm·R² / (r² + soften²)`，径向，在 `influence·R` 处平滑收尾 | 把星点拉过来 |
| 吸积流耦合 | `v += (v_flow − v) · k · dt` | 注入角动量、圆化轨道、缓慢内落 |

**引力是纯径向的中心力，不产生任何力矩，所以角动量守恒** —— 星点进来是什么轨道，
就沿着什么轨道走。这保证了"椭圆就是椭圆"，不会被某个人造力扭成别的形状。

**吸积流耦合是速度耦合，不是力。** `v_flow` 取当地圆轨道的切向速度：

```js
vFlow = sqrt(a · r) · flowInflow          // 当地圆轨道速度，刻意略低于 1
k     = flowCoupling · 包络(r)            // 只在近区生效
v    += (切向单位向量 · vFlow − v) · k · dt
```

它的效果有两层：

- **方向**：把速度从"径向俯冲"拖向"切向环绕"，于是星点从下坠逐渐转成绕行；
- **大小**：把速度拖向当地轨道速度，而 `flowInflow < 1` 让目标永远略低于圆轨道
  速度，于是圆化之后还会持续缓慢内落，最终被吞没。

### 4.2 为什么必须是"速度耦合"，不能是"切向力"

标定过程中试过最直觉的写法：在引力之外再加一个**切向力** `a_t = swirl · a`。
结果**所有星点最后都逃逸了**。

原因是切向力垂直于半径，始终与运动方向同向，**一直在对星点做正功**——
它把能量源源不断地灌进去，星点越转越快，最后直接飞出引力井。

速度耦合不做事：它把 `v` 拖向一个**固定的目标速度**，是纯粹的耗散项。
星点转速超过流场就被拖慢，低于流场就被带快，最终稳定在流场速度上。

> **改动提醒**：如果将来想调整环绕观感，请继续用"改 `v_flow`"的思路（改速度），
> 而不要加回切向力。这是一个踩过的坑。

### 4.3 星点靠自己绕不起来（角动量预算）

这一节解释为什么必须引入吸积流耦合，而不是"让引力自己解决"。

圆轨道角动量 `L_c(r) = r · v_c(r) = sqrt(gm)·R·sqrt(r)`。
而星点相对黑洞的角动量最多只有 `L = b · v`，其中 `b ≤ influence·R` 是撞击参数，
`v` 是相对速度（约等于黑洞自身的移动速度 34~68 px/s）。

代进去会发现：在这套尺度下（球半径约 24px、相对速度约 50px/s），**几乎全部星点的
角动量都不足以支撑一个位于球外的圆轨道** —— 差着一到两个数量级，所以它们全都
径向下坠、直接落进视界。

这不是实现问题，是物理事实：真实吸积盘里的物质之所以绕行，是因为它**本来就带着
轨道角动量进来**（来自伴星或分子云），而不是因为它被径向吸过来的。纯径向坠落的
物质不可能绕行。

所以吸积流耦合不是"作弊"，而是把"物质被卷入吸积流后获得角动量"这一过程显式建模。
调参时记住：**`flowCoupling` 本质上决定"吸积流有多强"，它同时决定轨道半径与圈数。**

### 4.4 椭圆 → 圆 是怎么发生的

三条相互制衡的机制：

1. 星点带着几乎为零的角动量俯冲进来 → 轨迹是一条**极扁的椭圆**（近似径向下坠）；
2. 进入耦合区后，速度被逐帧拖向切向，径向落速被吃掉 → 轨迹**逐圈变圆**；
3. `flowInflow < 1` 让它永远略低于圆轨道速度 → 圆化之后继续**缓慢内落**。

用数值标定（见 4.7）得到的典型半径演化：

```
9.0 → 8.3 → 7.6 → 7.0 → 6.5 → 6.0 → 5.6 → 5.1 → 4.5   ← 俯冲段，越来越快
                  → 3.5 → 2.8 → 2.7 → 2.5 → 2.4 → 2.3   ← 被抓住，开始环绕
                  → 2.1 → 2.0 → 1.8 → 1.6 → 1.4 → 1.2 → 1.1  ← 圆化 + 缓慢内落
```

前半段是椭圆（扁的），后半段接近圆 —— 就是用户要的"先椭圆、后圆"。
**`flowCoupling` 是唯一的调节旋钮**：

| 取值 | 效果 |
| --- | --- |
| 偏小（4~6） | 轨道更扁、更耐看，但捕获更慢，部分星点会直接落进去 |
| 偏大（15~20） | 更早被抓住、轨道更圆，但圆化太快，看不出"椭圆"这一段 |

### 4.5 自由星：速度积分，不是橡皮筋

**这是全项目最容易改错的一处。** 早先的版本给星点存了「原位 `(x,y)` + 位移
`(dx,dy)`」两套坐标，位移由一个弹簧-阻尼系统拉回原位。那种写法有两个后果：

- 星点的位置被弹簧绑在原位附近，**根本没有惯性** —— 引力只是把它"掰弯"一下，
  松手就弹回去；
- 于是"引力捕获"只能靠一条硬边界实现：一碰线就吸附到固定轨道上，
  看起来就是"碰到就跟着转圈"。

现在**每颗星只有一份真实速度，位置完全由速度积分得到**：

```
v += a · dt
x += v · dt
```

加速度累加进速度、速度再累加进位置，**惯性就是这两次积分自然产生的**：
星点进入引力范围后先是几乎无感（`t²` 式的软化势在边缘趋近 0），越靠近加速度越大，
于是它肉眼可见地"醒过来"、加速、并沿着弯曲的轨迹冲过去。

速度回归基线只在**脱离所有引力井之后**才发生：

```js
if (!s.inGravity) v += (baseline − v) · dt / relaxSec
```

`inGravity` 由 `blackhole.attract` 每帧置位、由 `stars.update` 读完即清
（自纠正：黑洞若在星点仍在井内时被回收，下一帧也能自动恢复平静）。
**井内必须是纯惯性** —— 只要井内也做回归，星点就会一边被吸一边被拖，
那种"被拽住又滑脱"的观感正是橡皮筋模型的老毛病。

### 4.6 尾流：运动本身的痕迹

尾流由 `scene/trail.js` 提供，它对"黑洞"一无所知，只做一件事：
**按固定时间间隔把位置点记下来，连成一条由旧到新、由淡到浓、由细到粗的折线。**

```js
push(x, y, dt)     // 累积时间，够一个采样间隔就记一个点，超出容量丢最旧的
draw(ctx, alpha, width, rgb)
```

由此自动得到三个性质：

- **长度 = 速度 × trailSpan**。快的东西尾巴长、慢的短，静止时收缩成一个点 ——
  完全不需要"开关"或"进入某状态才开始画"。
- **与帧率无关**。按时间间隔采样而不是每帧一个点，60Hz 和 120Hz 得到同样的长度。
- **通用**。星辰与流星用的是同一份实现，只是参数不同。

**亮度随速度渐显**（`stars.drawTrails`）：

```js
vis = clamp((|v| − trailMinSpeed) / (trailFullSpeed − trailMinSpeed), 0, 1)
```

星场基线漂移只有 1.2~8.2 px/s，远低于 `trailMinSpeed = 25`，所以平时完全没有尾流；
被引力加速到 150 px/s 时达到满亮度。**从"无尾流"到"满尾流"是一个连续渐显的过程**——
这正是解决"进入黑洞就突然长出尾巴"的关键：尾流不是被某件事触发的，而是随速度长出来的。

另外尾流必须画在**星点之前**，星点才像是领着这条尾巴走。

**瞬移必须处理，而且要分两种：**

| 情况 | 做法 | 原因 |
| --- | --- | --- |
| 吞没后重生、视口变化后重建星场 | `trail.reset()` | 前后两段轨迹毫无关系，留着会从旧位置拉出一条长线 |
| 出界后从对侧**回绕** | `trail.shift(dx, dy)` | 位移对星点与轨迹是同一个，整体平移之后还是原来那条尾巴 |

回绕这一条曾经漏掉过：只挪星点、不动轨迹，最旧的点留在屏幕这头、最新的点到了
那头，两点之间会凭空连出一条**横贯整个画面的亮线**，一闪即灭。
慢速漂移的星因为 `vis` 门槛根本不画尾流，所以这个 bug 只在"刚被黑洞甩出画面、
速度还很快"的星上暴露 —— 也正因为如此，它看起来很像"流星太快了"。
处理时位移量要用 `目标坐标 − 当前坐标`，而不是一个固定的 `宽 + 2×wrap`：
星点回绕时的实际坐标略超出边界，用固定值会让尾部与头部错开几个像素。

### 4.7 参数是怎么定的

这套力学的观感对参数非常敏感，靠肉眼猜很容易调偏，所以用一次性数值仿真做了标定：
把黑洞固定在原点，让星点以不同撞击参数掠过，统计**圈数、被吞没耗时、半径演化曲线**，
再据此选参数。标定脚本是临时的，没有留在仓库里。

如果将来要改 `gm` / `flowCoupling` / `influence`，建议照同样的方式先跑一遍数值，
重点看两个指标：

1. **半径演化曲线**有没有"俯冲 → 环绕 → 缓慢内落"三段；
2. **圈数**是否在 2~4 之间（太少看不出环绕，太多像永动机）。

**改半径要连带换算。** `influence` / `gm` / `flowInner` / `flowRange` 都是以 R 为
单位或与 R 挂钩的量，只改 `radiusMin` / `radiusMax` 会让整个引力场在
**像素尺度**上一起缩水，观感完全变样。本次把半径从 18~30 收到 15~25 时，
是按"像素尺度不变"重新锚定的：

| 量 | 锚定条件 | 原 → 现 |
| --- | --- | --- |
| 作用半径 | `influence × R` 保持 ≈ 156px | 6.5 × 24 → 7.8 × 20 |
| 远场加速度 | `gm × R²` 保持 1.5e6 | 2600 × 576 → 3750 × 400 |
| 耦合带 | `flowInner / flowRange × R` 保持 36 / 120px | 1.5、5.0 → 1.8、6.0 |

标定验证：同一个撞击参数下，缩小前后是 `落 16.7s / 0.17 圈` 对 `落 16.7s / 0.18 圈`，
轨迹一致。只有 `soften`（1.2R）和吞没半径 R 本身随 R 等比缩小 —— 这正是想要的效果：
球变小了，贴着球面的那点强引力也跟着收紧。

### 4.8 黑球本体与进出场

造型不是一个纯黑圆，而是一个**中心纯黑、往外渐变到完全透明**的球：

```js
core = bh.r * (1 - C.edgeSoft)                        // edgeSoft = 0.3
g = ctx.createRadialGradient(bh.x, bh.y, core, bh.x, bh.y, bh.r);
g.addColorStop(0, 'rgba(0, 0, 0, 1)');                // 内半径起：纯黑
g.addColorStop(1, 'rgba(0, 0, 0, 0)');                // 外沿：完全透明
```

径向渐变的**内半径**取 `(1 − edgeSoft)·R`：内圈以内是纯黑（渐变在首个色标
之内延续该颜色），只有最外那 `edgeSoft·R` 一圈是过渡带。两点说明：

- **颜色始终是黑，渐变的只是 alpha。** 所以渐变带是"越来越淡的黑"，
  以 `source-over` 叠在星空上，观感是星光被一层层压暗，而不是蒙上一层灰。
- **能看见的实心黑盘只有约 `0.7R`**，边缘那 30% 是化开的过渡带。
  这带来一个额外好处：星点贴近时本来就在降透明度（`smoothstep(0.7R, 1.5R, r)`），
  现在它消失的位置正好落在半透明的边缘里 —— 沉进一个化开的边界，
  比沉进一条硬边更有说服力。

不用纯黑圆，是因为纯黑圆的边缘太清楚，在星空上像贴上去的一个圆片；
渐变之后边缘把星光吃掉，才像一个真的把光吸走的东西。

除这条渐变边缘之外**没有**外发光、光子环、吸积盘、边缘流光 —— 那些成圈的亮环
会把视界轮廓裹成一层厚高光，既抢戏，也让黑洞失去干净的剪影。现在的取舍是：
让黑洞彻底"沉默"，把画面上所有动态都交给被它卷住的星。

它必须**最后绘制**：所有星与尾流画完之后才盖上去，被吞没的星才像是沉进球里。

进出场复用同一个淡入淡出系数：

```js
fade = smoothstep(0, 1, age / fadeInSec)      // 时间上淡入
     × smoothstep(0, R*3, 距屏幕边缘的距离)     // 空间上贴边淡出
```

入场边距取 `R * influence`，与引力作用半径一致；回收判定在
`R * (influence + 2)` 之外 —— 那时 `fade` 早已归零，不会看到消失。

吞没前还会连续降低透明度（`smoothstep(0.7R, 1.5R, r)`），让星点与尾流一起
"沉"进去，而不是在球边被硬切一刀。

## 5. 文案系统

### 5.1 单一数据源

`data/texts.txt` 是唯一数据源，一行一段：
空行忽略，`#` 开头为注释。

由于 `file://` 下 `fetch` 被拦截，`src/data/texts.fallback.js` 保存了一份
自动派生的内置副本。两者内容必须一致，因此：

```bash
npm run build:texts      # node scripts/build-texts.mjs
```

**每次改完 txt 都要跑一次。** 该脚本读取 txt、过滤注释与空行、
用 `JSON.stringify` 逐个转义后写出 JS，会打印实际条目数，便于核对。

**`src/data/texts.fallback.js` 是生成物，不要手改**，下次构建会被覆盖。

### 5.2 加载策略

`texts.js` 的 `load()` 永不 reject：

```
location.protocol === 'file:'  → 直接用内置副本
fetch 失败 / 非 2xx / 结果为空 → 用内置副本
否则                           → 用 fetch 结果
```

因此无论以哪种方式打开，页面都不会因为文案加载失败而空白。

### 5.3 轮播时序

`ui/answer-text.js` 的循环：

```
等待 startDelayMs
┌─ 取文案 → 复位动效 → 等 50ms → 加 .in
│  等 fadeMs + rand(holdMin, holdMax)          // 停留
│  移除 .in、加 .out
│  等 fadeMs + rand(gapMin, gapMax)            // 空档
└─ 回到取文案
```

三个时间常量（`fadeMs` / `hold*` / `gap*`）全在 `config.text` 里。
当前配置：淡入淡出各 1500ms、停留随机 5000~8000ms、空档 300~600ms，
单条周期约 **8.3~11.6 秒**。

> 调这一组参数时注意：`fadeMs` 同时决定淡入与淡出，所以它每调一次，
> 周期会以两倍于该值变化。另外 CSS 的 `transform` 位移固定为 52px，
> 淡入淡出拉得很长时（>2s）会让文字显得"飘得太慢"，必要时同步调 `--text-shift`。

**`fadeMs` 与 CSS 的同步**：`answerText.start()` 会把 `fadeMs` 写入 CSS 变量
`--text-fade`，`styles/text.css` 的 `transition` 引用该变量。
所以**只改 JS 一处即可**，不要再去 CSS 里写死时长。

### 5.4 reset() 里那两行不能删

```js
el.style.transition = 'none';
void el.offsetWidth;          // 强制回流
el.style.transition = '';
```

切换 `textContent` 与切换 class 若发生在同一帧，浏览器会把样式变更合并计算，
新文案就会直接以 `.in` 的终态出现、看不到淡入。强制回流把两次变更拆到不同帧。
`void` 是为了让 linter 知道这是有副作用的读操作。

## 6. 代码约定

- 每个文件一个 IIFE，顶部 `'use strict'`，形如
  `var NS = global.AnswerBook || (global.AnswerBook = {});`。
- 注释用中文，解释**为什么**而不是复述代码在做什么。
- 不在业务代码里写裸数字，参数一律进 `config.js` 并附单位说明。
- 坐标、半径、速度统一使用**秒**与**CSS 像素**，不用毫秒。
- 绘制函数保持无副作用：不改模块状态，只画。
- 更新逻辑与绘制逻辑分离（`update(dt)` / `draw()`），便于单独调参。
- 不使用箭头函数、解构、模板串等现代语法糖，维持 ES5 基线；
  `data/texts.js`、`ui/answer-text.js` 中的 `Promise` 是有意保留的唯一例外。

## 7. 静态校验

项目不含测试。提交前跑：

```bash
npm run check
```

它做两件事：

1. `scripts/check-syntax.mjs` —— 递归收集 `src` 与 `scripts` 下所有 js/mjs，
   逐一 `node --check`，任何一个失败就以非零码退出；
2. `scripts/audit-config.mjs` —— **配置键引用审计**，见下。

### 7.1 为什么要单独写一个配置审计

代码里写 `C.speedMax` 而 `config.js` 的对应段落里没有这个键，**不会报错**：
`undefined` 参与运算得到 `NaN`，画面照样"能跑"，只是那个参数悄悄失效了。
本次就踩过一次：`meteors.js` 用了 `C.speedMax`，配置里写的却是 `speedSpan`，
结果所有流星的速度都是 `NaN` —— 靠一个临时仿真脚本才抓出来。

审计的规则：

- **必须按段落比对**（`blackhole` / `stars` / `meteors` / `text`），
  不能在整份文件里搜键名 —— `blackhole` 段落也有 `speedMax`，
  整份搜会把缺失的键误判成命中，这一版审计最早就是这么漏的；
- 顺带检查值是否为数字（字符串键 `elId` / `source` 是白名单例外）；
- 反查"段落里定义了但代码里没用"的键，提示冗余。

### 7.2 语法与配置检查覆盖不到的

仍建议手工排查：

1. 新增模块后，`index.html` 里的加载顺序是否满足依赖；
2. **几何量是否可能为负或 NaN**（流星寿命、黑洞边距这类由坐标算出来的值）——
   本次用一次性仿真脚本验证过：生成几千次流星，检查起点在画面外、
   寿命为有限正数、寿命结束时确实飞出画面；以及尾流在回绕前后是否仍连续。
   这类脚本是临时的，没有留在仓库里，但**改生成几何时值得照样跑一遍**；
3. 文案条数变化后，是否重跑了 `build:texts`。

## 8. 扩展指南

### 加一个场景元素（例如"星尘粒子"）

1. 新建 `src/scene/dust.js`，仿照 `meteors.js` 的结构导出 `list / update / draw`；
2. 在 `index.html` 里插到 `trail.js` 之后、`blackhole.js` 之前；
3. 在 `main.js` 的 `frame()` 里按"更新 → 绘制"补两行，注意与黑洞的前后层次；
4. 参数加进 `config.js` 的 `dust` 段。

**只要它在动，就能白拿一条尾流**：在实体上放一个
`trail: NS.trail.create(spanSec, steps)`，每帧 `push(x, y, dt)`，
绘制时 `draw(ctx, alpha, width, rgb)` 即可。流星就是这么做的。

### 给黑洞加视觉特征

当前造型是刻意留白的：中心一个纯黑、边缘渐变到透明的小球，除此之外什么都没有。
加任何东西前先想清楚是不是真的需要 —— 见 4.8 的取舍说明。

真要加（例如一条引力透镜的细弧），在 `blackhole.js` 里写一个 `drawXxx(bh)`，
再决定它和黑球的层叠关系：

- 想被黑球遮住（在球体之后）→ 调在 `draw()` 循环里、填圆之前；
- 想压在黑球之上 → 填圆之后，但注意会破坏"星点沉进球里"的观感；
- 如果只想让边缘再"毛"一点，优先调 `edgeSoft`，而不是另加一层发光。

### 调整黑洞的力学

先读 4.1 ~ 4.4，再按 4.7 的方式**先用数值仿真标定再改参数**。
两个最容易踩的坑：

- **不要加切向力**（4.2），星点会被持续加速直到逃逸；
- **不要试图靠"削弱引力"让星点自然绕行**（4.3），角动量差着数量级，做不到。

### 把项目改成 ES Modules

各文件的 IIFE 内容基本可以原样搬进模块作用域，只需：

1. 把 `NS.xxx` 的读写换成 `import` / `export`；
2. `index.html` 的十余个 `<script>` 合并为一个 `<script type="module" src="src/main.js">`；
3. **注意**：此后必须通过 HTTP 访问，`file://` 双击打开会失效。

### 2.4.0

- **尾流改为通用模块**：新增 `scene/trail.js`。尾流不再由"是否入轨"触发，
  而是**运动本身的痕迹** —— 按固定时间间隔记录位置点连成折线，
  长度 = 速度 × `trailSpan`，亮度随速度渐显（`trailMinSpeed` ~ `trailFullSpeed`）。
  解决了"进入黑洞才突然长出尾巴"的突兀感，并且星辰与流星（`meteors.js`）
  共用同一份实现，流星原有的手算线段端点逻辑一并移除。
- **黑洞力学重做为真实积分**：删除全部参数化轨道（`orbit` 状态、
  `enterOrbit` / `advanceOrbit`、`captureRadius` / `orbitOmega*` /
  `orbitSettleSec` / `orbitLife*` / `orbitDir`）。现在只有两项力：

  | 力 | 作用 |
  | --- | --- |
  | 软化平方反比引力（径向，无矩） | 角动量守恒 → 轨道保持为真椭圆 |
  | 吸积流速度耦合（耗散） | 注入角动量、圆化轨道、缓慢内落 |

  星点全程只是一个被积分的质点，没有"入轨"这一刻，因此"俯冲 → 环绕"完全连续。
- **记录两条标定结论**（均已写入 4.2 / 4.3）：切向力会持续做功导致星点逃逸；
  且在本项目尺度下星点自带的角动量比圆轨道所需小一到两个数量级，
  "纯引力自然绕行"物理上不可能，必须由吸积流提供角动量。
- 新参数：`blackhole` 的 `gm` / `soften` / `taper` / `flowCoupling` /
  `flowInner` / `flowRange` / `flowInflow`；`stars` 与 `meteors` 的 `trail*` 系列。

### 2.3.0

- **星点模型重做：引入真正的惯性**。废弃「原位 + 位移偏移」的弹簧-阻尼模型，
  改为每颗星持有真实速度 `(vx, vy)` 与基线漂移 `(bvx, bvy)`，
  位置完全由速度积分得到。星点被引力推着走多远、走多快都会真实累积，
  不再被弹簧拉回原位。相应移除 `spring` / `damping` / `maxOffset` / `(dx, dy)`，
  新增 `stars.relaxSec`（脱离引力井后速度回归基线的时间常数）。
- **入轨由动量决定**：新增 `enterOrbit()`，把星点当下的实际速度分解为径向/切向
  分量，环绕方向 100% 来自惯性，角速度初值取 `v_t / radius`，
  内落速率取径向速度。彻底消除"碰到边界就被吸附进固定轨道"的跳变。
